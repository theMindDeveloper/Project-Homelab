# Alerting

**A message on the phone when something breaks, and silence when nothing
does.** Both halves are hard. This page is about both.

Until October 2026 this lab had no alerting at all: Prometheus collected,
Grafana drew, and a broken thing was noticed when someone looked. Now Grafana
sends alerts to a Telegram bot. Step by step: [runbook 23](../runbooks/23-alerts-to-telegram.md).
Files: [`compose/monitoring/grafana/provisioning/alerting/`](../compose/monitoring/grafana/provisioning/alerting/),
rules generated by [`scripts/grafana/gen_alerts.py`](../scripts/grafana/gen_alerts.py).

---

## The choices

### Grafana alerting, not Alertmanager

The classic Prometheus way is Prometheus rules plus a separate **Alertmanager**
container. This lab uses **Grafana's built-in alerting** instead:

| | Grafana alerting | Prometheus + Alertmanager |
|---|---|---|
| Extra containers | none, Grafana already runs | one more (Alertmanager) |
| Alert on **logs** (Loki) | yes, same rule format | needs Loki's own ruler as well |
| Telegram | built in | built in |
| Rules as files | yes (provisioning) | yes |
| Where you see state | Grafana → Alerting | Alertmanager UI + Prometheus |

Several rules here need Loki (failed SSH logins, "the firewall stopped
logging"), and one mixes Loki and Prometheus in a single rule. That decided it.

### A Telegram bot of your own, not an AI agent and not a paid service

Grafana talks to the Telegram Bot API directly. You create a bot with
**@BotFather** in two minutes, and Grafana posts into your chat with it.

- **Nothing in between.** No relay service, no AI agent reading the alert and
  paraphrasing it (this lab has one, and routing alerts through it would cost
  tokens on every message and add a moving part to the one path that must
  work when everything else is broken).
- **The token can only post as that bot.** If it leaks, `/revoke` in BotFather
  replaces it.
- **It lives in an env file** (`alerting.env`, mode 600, not in Git) and reaches
  Grafana as an environment variable.

## How a Grafana alert rule works

One rule = a few queries, a condition, and some timing.

```
A  (query)      max by (node) (up{job=~"proxmox-host|other-hosts"}) < bool 1     -> per node: 1 = down, 0 = up
C  (threshold)  A > 0                                                              -> true for every node that is down
for: 2m                                                                            -> must stay true for 2 minutes
labels: severity=critical                                                          -> decides who/when (routing)
annotations: summary="{{ .Labels.node }} is DOWN"                                  -> the text of the message
```

- **One rule, many alerts.** The query returns one series per node, so one
  rule produces a separate alert per node: "pve is DOWN" and "pi is DOWN" are
  two alerts that come and go independently.
- **`for:` separates a signal from noise.** Without it, one failed scrape
  pages you. With `for: 2m`, the condition has to hold across several
  evaluations. An alerting system people mute is worse than none, because it
  produces the *feeling* of coverage.
- **States:** *Normal* → *Pending* (condition true, waiting out `for`) →
  *Firing* (message sent) → back to *Normal* ("resolved" message).
- **No data:** what should happen when the query returns nothing at all? Here
  always `OK`, because "no data" usually means "this thing doesn't exist right
  now" (a game panel on a switched-off node). A dead exporter is caught by its
  own rule instead (see the traps).

### The pattern used for every rule here

Every query is written to return **1 = problem, 0 = fine**, with PromQL's
`bool` comparison, and the threshold is always just "> 0":

```promql
max by (node, mountpoint) (1 - node_filesystem_avail_bytes / node_filesystem_size_bytes) > bool 0.9
```

One shape for all rules makes them easy to read, easy to test (the query alone
tells you what would fire) and impossible to get the threshold backwards.

## Routing: who gets what, when

```
                            ┌─ severity = game     -> telegram-games   any time, no "OK again"
every alert ── policy tree ─┼─ severity = warning  -> telegram         muted 23:00-08:00 (Berlin)
                            └─ everything else     -> telegram         any time   (= critical)
```

| Piece | File | What it does |
|---|---|---|
| **Contact points** | `contact-points.yml` | *where* to send: two Telegram receivers, same bot. `telegram-games` has "resolved" messages switched off |
| **Notification policy** | `policies.yml` | *which* alert goes to which contact point, grouped by `alertname` + `node`, repeated at most every **4 h** |
| **Mute timing** | `policies.yml` (`muteTimes`) | "night": 23:00-24:00 and 00:00-08:00, Europe/Berlin. Attached to the warning route only |
| **Template** | `templates.yml` | the message text |

A muted warning is not lost: if it is still firing at 08:00, it is sent then.

### What arrives on the phone

```
🔴 pve3 is DOWN
Prometheus can't reach pve3 for 2 minutes.
Open Grafana

✅ OK again: pi / is over 80% full
Open Grafana

🎮 Minecraft stopped (amp)
It was running and is not anymore. If you stopped it yourself, ignore this.
Open Grafana
```

Short on purpose: one line saying what, one line saying why it matters, one
link. Everything else is one tap away in Grafana.

## The rules

| | Rule | Fires when | `for` |
|---|---|---|---|
| 🔴 | Host down | pve, the Pi or the NAS cannot be scraped | 2 min |
| 🔴 | Guest with autostart stopped | a VM/LXC with "start at boot" is not running, **while its node is on** | 5 min |
| 🔴 | AdGuard down | the house DNS stopped | 3 min |
| 🔴 | Disk over 90 % | any filesystem on any monitored machine | 10 min |
| 🔴 | Proxmox storage over 90 % | any Proxmox storage | 10 min |
| 🔴 | CPU over 85 °C | any monitored machine | 5 min |
| 🔴 | Internet down | the FRITZ!Box reports the WAN link down | 3 min |
| 🟠 | Disk / storage over 80 % | as above, earlier | 30 min |
| 🟠 | Disk full within 7 days | `predict_linear` over 6 h says < 0 in 7 days | 2 h |
| 🟠 | Power-saving node off | pve2 or pve3 cannot be scraped ("pve3 is off", then an OK message when it's back) | 2 min |
| 🟠 | RAM over 90 % | any monitored machine | 15 min |
| 🟠 | CrowdSec detected an attack | a CrowdSec scenario matched in the last 10 min | 0 |
| 🟠 | Many failed SSH logins | > 10 in 10 min on LXC 102 (Loki) | 0 |
| 🟠 | OPNsense stopped sending logs | no firewall line for 30 min **while pve2 is on** (Loki + Prometheus) | 5 min |
| 🟠 | Log collection stopped | no log line at all for 15 min (Loki) | 5 min |
| 🟠 | Monitoring target down | any exporter not answering | 10 min |
| 🟠 | New device joined the network | the FRITZ!Box's known-device count went up | 0 |
| 🟠 | FRITZ!Box update available | firmware update waiting | 1 h |
| 🎮 | Game server stopped | a game server that was running in the last 10 min is not now | 1 min |

**"Internet down" arrives after the internet is back.** The alert fires while
the line is down, but Telegram is on the other side of that line. You get the
message once it's back, which is still useful: it tells you it happened, and
for how long.

## The traps

Every one of these was in the first version of the rules or was found while
testing them. Each one would have made an alert either never fire or fire for
nothing.

### 1 · `or vector(0)` hides a dead exporter

```promql
(max(fritz_wan_phys_link_status) or vector(0)) < bool 1     # wrong
max(fritz_wan_phys_link_status) < bool 1                    # right
```

`or vector(0)` turns "no data" into 0. When the router exporter itself stopped,
"no data" became "link status 0", and the rule would have said **internet down**
while the internet was fine. Without it, a dead exporter gives "no data" →
`OK`, and the separate rule **Monitoring target down** (`up == 0`) reports the
real problem.

It nearly happened for real: the exporter's default listen address made it
unreachable after deploying, and this rule was minutes away from a false 🔴 at
night.

### 2 · A comparison without `bool` filters

```logql
(sum(count_over_time({job=~".+"}[15m])) or vector(0)) < 1        # never fires
(sum(count_over_time({job=~".+"}[15m])) or vector(0)) < bool 1   # 1 when no logs
```

Without `bool`, `< 1` *keeps* the series when the value is below 1 and keeps
its value, which is 0. The threshold "> 0" then sees 0 and never fires. With
`bool`, the result is 1 exactly when there are no logs. (Here `or vector(0)` is
correct, because "no logs at all" is the very thing being detected.)

### 3 · Stale series break `predict_linear`

"Disk full within 7 days" fired the moment it was first tested. The data in its
6-hour window included series from **before** a `node` label was added to the
scrape config: same disk, different labels, a regression over half the data.
The fix is to only predict on correctly labelled series (`node!=""`). Any rule
over a long window should be checked against what happened in that window.

### 4 · Machines that are off on purpose

pve2 and pve3 are often switched off to save power. A naive rule set turns that
into a night of messages:

| Naive rule | Problem | Fix |
|---|---|---|
| Host down | fires for pve2/pve3 every evening | no 🔴 for pve2/pve3 (`node!~"pve2\|pve3"`); instead a soft 🟠 "Power-saving node off": a warning, so never at night, and "fine if you switched it off yourself" |
| Guest with autostart stopped | every guest on pve2 counts as "stopped" | `and on (node) (up{job="proxmox-host"} == 1)`: only while its node is up |
| OPNsense stopped logging | OPNsense lives on pve2 | a two-query rule: Loki count **and** "pve2 is up" |

The third one is the only rule that mixes data sources. Grafana does that with
a *math* expression over two queries:

```
A (Loki):        sum(count_over_time({job="opnsense"}[30m])) or vector(0)
B (Prometheus):  max(up{job="proxmox-host", node="pve2"}) or vector(0)
C (math):        $A < 1 && $B == 1
```

### 4b · A "<" in a message text drops the whole message

"Disk full within 7 days" fired, but nothing ever reached Telegram. Its text
said "will be full in < 7 days". The contact point sends with `parse_mode`
HTML, so Telegram read `< 7` as a broken HTML tag and rejected the whole
message (400 "Unsupported start tag"). Grafana only logs that error, every
5 minutes. The text now says "within 7 days", and `gen_alerts.py` refuses any
`<` or `&` in alert texts, so this cannot come back.

### 5 · `$` means three different things

- In **docker compose** files, `$` starts a variable. A regex like `($|/)` in a
  compose command is an error ("invalid configuration file" is all UGOS says).
  Write `$$` or avoid it.
- In **Grafana contact-point files**, `${TELEGRAM_BOT_TOKEN}` is replaced by
  the environment variable. That is how the token stays out of the file.
- In **Grafana alert-rule files**, `$A` is **not** replaced, it is passed to the
  math expression as it is. Writing `$$A` (as the compose habit suggests) leaves
  a literal `$$A` and the rule fails to parse. This was caught only by loading
  the files into a test Grafana, see below.

### 6 · An alert that cannot tell who caused it

"Game server stopped" fires when you stop the server yourself. The game panels
know who pressed stop (activity log), but the monitoring user is not allowed to
read it, so the message says "if you stopped it yourself, ignore this". Honest
beats clever. Reading the activity log is the planned improvement.

### 7 · An excluded guest is a decision, not a fix

One LXC is set to "start at boot" but is stopped on purpose for now. Instead of
letting the rule fire forever, it is excluded by ID **with a comment pointing to
the open decision**. An exclusion without a reason is how alert rules rot.

## Testing alerts before they reach the phone

A rule that has never fired is a guess. These were used here, in this order,
and every one of them caught something:

1. **Run each query against live data.** Every rule's query returns 0 or
   nothing today. A rule whose query returns 1 right now would fire on deploy.
   Two did (trap 3, and the excluded guest).
2. **Unit-test the logic with `promtool test rules`.** Feed made-up series
   ("runs for 5 minutes, then stops", "panel disappears") and assert the result
   at given times. That is how the game rule was proven to fire after a stop,
   end after 10 minutes and stay quiet when a node is switched off.
3. **Load the files into a throwaway Grafana** of the same version (a tarball
   on any Linux machine, a second port, a temp data folder). If Grafana starts
   and lists all rules, contact points, routes and mute timings, the files are
   right. This caught trap 5. A broken alerting file can stop the real Grafana
   from starting, so this step matters.
4. **Render the message template** with Grafana's template-test API and fake
   alerts (firing and resolved).
5. **Contact point → Test** in the real Grafana sends a real message.

Commands for all five: [runbook 26](../runbooks/26-test-grafana-changes-safely.md).

## Living with it

- **Grafana → Alerting → Alert rules** shows every rule and its state.
- **Silences** mute a specific alert for a while: "silence `node=pi` for one
  hour" before rebooting the Pi. Better than turning a rule off and forgetting.
- **Rules cannot be edited in the Grafana UI.** They come from files, so a
  change is a change to `gen_alerts.py`, a regenerated `rules.yml`, a pull
  request and a Grafana restart. That is slower than clicking, and it means
  every rule has a history and a reason.
- **If an alert annoys you, fix the rule, don't mute the chat.** A muted chat
  also mutes the 🔴 at 3 a.m.
